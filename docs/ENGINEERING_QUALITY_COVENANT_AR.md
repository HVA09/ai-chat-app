# ميثاق الجودة الهندسية والتوافق والاستمرارية

**الإصدار:** 1.0  
**تاريخ الاعتماد المبدئي:** 15 نوفمبر 2026  
**النطاق:** هذا الميثاق معيار إلزامي مشترك للمشاريع الثلاثة والمنظومة المستقبلية. يُطبّق مع خطة كل منتج ولا يستبدلها.

## الغاية

نريد بناء أنظمة مفهومة، موثقة، قابلة للصيانة والتوسع، ومتوافقة داخلياً وخارجياً؛ لا نريد سلسلة ترقيعات متكررة أو تقنيات مجهولة أو إعادة كتابة بسبب قرارات غير مدروسة. لا يمكن ضمان غياب الأخطاء تماماً، لكن يمكن تقليل احتمالها واكتشافها مبكراً واحتواء أثرها ومنع تكرارها باختبارات وأدلة.

**القاعدة الأساسية:** لا نعتبر أي تغيير صحيحاً لمجرد أنه يعمل في حالة واحدة أو أن أداة ذكاء اصطناعي اقترحته أو أن البناء نجح. يجب أن يكون مفهوماً، متوافقاً، قابلاً للاختبار والتراجع، ومدعوماً بدليل.

## 1. التعلم من الأخطاء ومنع تكرارها

كل عطل مؤثر أو متكرر يتحول إلى معرفة هندسية دائمة:

1. إعادة إنتاج المشكلة وتحديد نطاق التأثر والنسخ والإصدارات المتأثرة.
2. جمع الأدلة: السجلات، request/correlation IDs، traces، metrics، stack traces، ونتائج الاختبارات.
3. تحليل السبب الجذري والعوامل المساهمة، لا معالجة العرض الظاهر فقط.
4. إضافة اختبار Regression يفشل قبل الإصلاح وينجح بعده، أو اختبار وقائي مكافئ عندما يتعذر إعادة الإنتاج.
5. معالجة السبب مع الحد الأدنى من التغيير الآمن، ثم تشغيل الاختبارات ذات الصلة واختبارات عدم التراجع.
6. توثيق الدرس والإجراء الوقائي ومؤشر التحقق في سجل الحوادث أو سجل القرارات.
7. مراقبة الإصدار بعد النشر، مع خطة رجوع أو تعطيل للميزة عند الحاجة.

لا نكرر إصلاح المشكلة نفسها من دون فحص سبب فشل الإصلاح السابق. لا نحذف اختباراً مزعجاً لإخفاء فشل حقيقي، ولا نعتبر زيادة عدد المحاولات دليلاً على حل المشكلة.

## 2. القرارات التقنية المعلومة (ADR)

لا نعتمد لغة أو إطاراً أو قاعدة بيانات أو مكتبة أو مزود خدمة جديداً قبل تسجيل قرار مختصر يتضمن:

- المشكلة والمتطلبات الوظيفية وغير الوظيفية التي نحلها.
- البدائل الواقعية التي تمت دراستها، بما فيها الإبقاء على التقنية الحالية.
- سبب الاختيار بناءً على الأداء والأمان والنضج والصيانة والتوافق والتكلفة والترخيص.
- الإصدارات المدعومة، ومتطلبات التشغيل، وحدود الموارد، ومخاطر الاعتماد على المزود.
- طريقة الاختبار والقياس والمراقبة، وطريقة الاستبدال أو التراجع.
- الأثر على بقية المشاريع والعقود والبيانات.

لا نعتمد تقنية لمجرد شهرتها أو حداثتها. نتحقق من الوثائق الرسمية، نشاط الصيانة، توافق الترخيص، الثغرات المعروفة، سجل الإصدارات، دعم المنصة، وسهولة استيراد/تصدير البيانات. لا نستخدم مكتبة مهجورة أو إصداراً غير مدعوم في مسار حساس من دون استثناء موثق وخطة إزالة. لا نغيّر لغة مشروع يعمل لمجرد أن لغة أخرى أسرع نظرياً.

كل قرار يوصف بوضوح بأنه **معتمد** أو **تجربة محدودة** أو **مقترح** أو **مرفوض**. لا تتحول التجربة إلى اعتماد إنتاجي بصمت.

## 3. سجل التوافق ومصدر الحقيقة

يحتفظ كل مشروع بمصفوفة توافق محدثة تغطي، بحسب ما ينطبق:

- إصدارات اللغات وأطر العمل ومديري الحزم وملفات القفل.
- نظام التشغيل والحاويات ونسخ قواعد البيانات ومحركاتها وإصدارات المخطط.
- عقود API وإصداراتها، وتنسيقات الرسائل والأحداث.
- المتصفحات والأجهزة المحمولة ودعم العربية وRTL/LTR.
- خدمات الاستضافة والتخزين والكاش والصفوف ومزودي الذكاء الاصطناعي وواجهاتهم.
- أدوات النسخ الاحتياطي والاستعادة والترحيل والمراقبة.

لا نستخدم عبارة «متوافق» من دون تحديد الإصدار والاختبار الذي أثبت ذلك. نثبت الإصدارات ضمن نطاقات واضحة، ونحدث الاعتماديات على دفعات صغيرة بعد قراءة ملاحظات الإصدار وتشغيل CI واختبارات التوافق. لا نستخدم `latest` أو تحديثاً جماعياً عشوائياً في الإنتاج.

يكون لكل نوع بيانات مصدر حقيقة واحد محدد. لا ننشئ مصدرين متنافسين للهوية أو العضوية أو الرصيد أو حالة الطلب، ولا ننفذ dual-write بين قاعدتين من دون بروتوكول اتساق وتعافٍ مثبت وموافقة معمارية.

## 4. الحدود المعمارية والتكامل

- لكل منتج مستودعه وقاعدة بياناته وأسراره ونشره واختباراته المستقلة.
- التكامل بين المنتجات عبر API أو أحداث موثقة ومصادق عليها، وليس عبر الوصول المباشر إلى قاعدة بيانات منتج آخر.
- لكل API عقد موثق وإصدار وسياسة مصادقة وصلاحيات وحدود طلب ومهلة وأخطاء معروفة.
- تغييرات العقود تتبع التوافق الخلفي: إضافة اختيارية أولاً، انتقال العملاء، قياس الاستخدام، ثم إزالة الإصدار القديم بعد فترة إهمال موثقة.
- لا نربط الخدمات بحيث يؤدي فشل خدمة اختيارية أو AI Core إلى توقف الوظائف الأساسية لمنتج آخر.
- نستخدم timeouts وbounded retries مع jitter وidempotency keys وcircuit breakers حيث تلزم؛ لا نعيد الطلبات غير الآمنة عشوائياً.
- نفضّل بنية بسيطة ذات حدود وحدات واضحة. لا نجزئ النظام إلى microservices أو نضيف message broker أو Kubernetes لمجرد التوسع النظري؛ نضيفها عند وجود حاجة وقياس يثبتان فائدتها.

## 5. جودة الكود ومراجعة التغييرات

- كل PR يعالج نطاقاً واضحاً ومحدوداً، ويشرح السبب والمخاطر والتوافق وخطة التراجع.
- لا تغييرات تشغيلية مخفية داخل PR توثيقي أو تحديث اعتماديات.
- نستخدم formatter وlinter وفحوص الأنواع والتحليل الساكن حيث تتوفر في التقنية المستخدمة.
- الكود يجب أن يكون قابلاً للفهم؛ لا نضيف abstractions أو طبقات عامة من دون حاجة موثقة.
- نعالج الأخطاء بوضوح ونحافظ على رسائل قابلة للتشخيص دون كشف أسرار أو بيانات شخصية.
- لا نبتلع الاستثناءات بصمت، ولا نعلن نجاح عملية قبل تأكيدها من الخدمة أو قاعدة البيانات.
- أي كود مولّد بالذكاء الاصطناعي يعامل كاقتراح غير موثوق حتى تتم مراجعته وتشغيل الاختبارات المناسبة؛ لا يُسمح له بتغيير بيانات إنتاج أو أسرار أو إعدادات حساسة دون بوابة تشغيل معتمدة.
- لا ندمج كوداً لا يستطيع الفريق تفسيره أو صيانته.

## 6. هرم الاختبارات وبوابات القبول

يختار كل تغيير الاختبارات المناسبة لطبيعته، ولا يكفي نجاح اختبار واحد:

1. Unit: المنطق والتحقق والحالات الطرفية.
2. Component/Contract: توافق المكونات والعقود وواجهات API.
3. Integration: قاعدة البيانات والتخزين والطوابير ومزودي الخدمات الوهميين أو التجريبيين.
4. End-to-End: تدفقات المستخدم الحقيقية، الأجهزة والمتصفحات وواجهات الطرف الثالث Sandbox.
5. Security: الصلاحيات، IDOR، عزل البيانات، إدارة الأسرار، فحص الاعتماديات، وسيناريوهات إساءة الاستخدام.
6. Data: سلامة المخطط والترحيل والمطابقة والنسخ الاحتياطي والاستعادة.
7. Performance/Resilience: الحمل والتزامن والثبات طويل المدة والانقطاع والتعافي عند الحاجة.

**كل Bug مؤثر يجب أن ينتج Regression Test.** ويجب اختبار المسارات السلبية، وليس النجاح فقط. لا نسمح بتخطي الاختبار المطلوب أو إخفاء Skip غير مبرر. الاختبار غير المنفذ يظل غير مثبت.

## 7. قواعد البيانات والترحيل وحماية البيانات

- مخطط قاعدة البيانات والترحيلات مصدران موثقان ومراجعان، مع ترتيب إصدارات وبصمات عند الحاجة.
- قبل أي ترحيل: نسخة احتياطية قابلة للاستعادة، تجربة على نسخة منفصلة، تقدير التوقف والمخاطر، وخطة rollback أو forward-fix معتمدة.
- التحقق من الأعداد والعلاقات والقيود والمجاميع المالية والبصمات بعد الترحيل؛ نجاح الأمر وحده لا يثبت صحة البيانات.
- لا تُختبر الترحيلات على قاعدة حية أو بيانات حقيقية عندما تكفي قاعدة disposable وبيانات اصطناعية.
- لا تُخزن الأسرار أو قواعد البيانات أو المرفقات الخاصة في مستودع عام.
- أقل صلاحية، وتشفير أثناء النقل والتخزين عند الحاجة، وسجل تدقيق، واحتفاظ وحذف واضحان.

## 8. الأمن والاعتمادية والتشغيل

الأمن جزء من التصميم وليس مرحلة تجميلية أخيرة:

- تهديدات الأصول وحدود الثقة ونقاط الدخول والصلاحيات تراجع قبل الميزات الحساسة.
- الأسرار عبر secret manager أو إعدادات البيئة المحمية، ولا تظهر في Git أو logs أو تقارير CI.
- فحص الاعتماديات والثغرات والأسرار وتحديثات الأمان ضمن CI.
- مراقبة زمن الاستجابة p50/p95/p99، ومعدل الأخطاء، والازدحام، وعمق الطوابير، واستهلاك الموارد، وصحة قواعد البيانات والخدمات.
- استخدام correlation/request IDs مع logs وtraces دون تسجيل محتوى حساس.
- تحديد SLOs وأهداف RTO/RPO عند تجهيز الإنتاج، وتجربة الاستعادة فعلياً لا الاكتفاء بوجود ملف Backup.
- نشر تدريجي أو feature flags أو canary عندما يتناسب ذلك مع البيئة، مع وسيلة واضحة لإيقاف التغيير.

## 9. الأداء والتوسع: لا ادعاءات بلا قياس

لا نعلن قدرة النظام على تحمل أعداد ضخمة أو «ملايين المستخدمين» اعتماداً على لغة البرمجة أو تصميم نظري. نحدد workload: المستخدمون المتزامنون، الطلبات في الثانية، أحجام البيانات والملفات، زمن الاستجابة المقبول، ونسبة الطلبات التي تستخدم GPU أو خدمات خارجية.

نضع اختبارات load وstress وsoak، ونقيس p95/p99 وerror rate وthroughput وCPU/RAM/DB connections/queue lag وتكلفة الطلب. ثم نحدد عنق الزجاجة ونوسّع الجزء اللازم فقط. نثبت حدود المعدلات والحصص والعزل حتى لا يستهلك عميل واحد موارد الجميع.

## 10. إدارة المعرفة ومنع الالتباس

لكل مشروع سجلات دائمة منفصلة:
- Roadmap: ما الذي سنبنيه ولماذا.
- ADR: لماذا اخترنا التقنية أو المعمارية.
- Continuity/Status: ما الذي يعمل فعلاً وما هو آخر commit ونتائج CI.
- Incident/Postmortem: ما الذي فشل وسببه وكيف منعنا تكراره.
- Compatibility Matrix: ما الإصدارات التي اختُبرت معاً.
- Release Record: ما الذي أُطلق وكيف نرجع عنه.

نميز دائماً بين **موجود في الكود** و**اختُبر** و**اجتاز CI** و**اختُبر خارجياً** و**نُشر** و**مقبول إنتاجياً**. لا نخلطها ولا نرفع الحالة من واحدة إلى أخرى من دون دليل.

## 11. تعريف الإنجاز (Definition of Done)

لا تعتبر الميزة أو الإصلاح مكتملاً حتى تتوفر، بحسب طبيعة التغيير:

- متطلبات ومعايير قبول واضحة.
- سبب التغيير ونطاقه والبدائل والمخاطر موثقة.
- مراجعة التوافق مع الإصدارات والعقود والمنتجات المتأثرة.
- اختبارات ناجحة بما فيها Regression والاختبارات السلبية ذات الصلة.
- لا أسرار أو بيانات خاصة في التغيير.
- تحديث الوثائق ومصفوفة التوافق وسجل الحالة.
- خطة نشر وتراجع ومراقبة عند التأثير التشغيلي.
- أدلة يمكن إعادة فحصها: PR/commit/CI/test report أو Sandbox report.

## 12. مراجعة دورية للميثاق

عند تكرار عطل من الفئة نفسها، أو ظهور تعارض إصدار أو فشل ترحيل أو حادث أمني، نراجع الميثاق ونضيف قاعدة وقائية واختباراً أو بوابة مناسبة. لا نضيف إجراءات شكلية لا تقلل خطراً فعلياً، ولا نخفف بوابة أمان بسبب الاستعجال.

## ملحق خاص بالمشروع

### AI Chat App

- يُفصل adapter مزود الذكاء الاصطناعي عن منطق المحادثات، وتُوثق واجهة موحدة وإصدارات النماذج وخصائص streaming/tool calls.
- أي تغيير في prompt أو model أو provider يمر على مجموعة تقييم ثابتة تشمل جودة الإجابة، الأدوات، العربية/الإنجليزية، زمن الاستجابة، الأخطاء والتكلفة.
- لا نبدأ إعادة فهرسة أو embedding job واسعاً قبل dry-run وتحديد الحجم والتكلفة وخطة الإيقاف والاستئناف.
- يجب اختبار streaming مع انقطاع الشبكة، انتهاء المهلة، إلغاء المستخدم، إعادة المحاولة، وتنظيف اتصالات قاعدة البيانات والموارد.
- أدوات المساعد لا تُنفّذ أفعالاً حساسة دون صلاحيات واضحة وتأكيد مناسب وسجل تدقيق.
- تبقى محادثات المستخدمين والملفات والذاكرة داخل حدود التطبيق؛ لا تُشارك تلقائياً مع AI Core أو منتجات أخرى.

## 13. الممارسات الاحترافية المرجعية (Industry Engineering Practices)

هذا القسم يحوّل الممارسات المنشورة لدى مؤسسات هندسية كبرى والمعايير المفتوحة إلى ضوابط عملية. لا يعني ذلك تقليد بنية شركة أخرى أو شراء أدواتها؛ نختار الممارسة التي تخفض خطراً مثبتاً وتناسب حجم المنتج وميزانيته.

### 13.1 إطار تقييم معماري مستمر

نراجع كل منتج وفق ستة محاور مترابطة:
1. التميز التشغيلي: سهولة التشغيل، وضوح المسؤوليات، أتمتة الأعمال المتكررة، وسجلات تشغيل قابلة للاستخدام.
2. الأمن والخصوصية: الهوية والصلاحيات وحماية البيانات وسلسلة توريد البرمجيات والاستجابة للحوادث.
3. الاعتمادية: تحمل الأعطال، استعادة الخدمة والبيانات، تقليل نطاق الفشل، والتدهور المنضبط.
4. كفاءة الأداء: زمن الاستجابة والسعة واستهلاك الموارد وقابلية التنبؤ تحت الحمل.
5. كفاءة التكلفة: تكلفة الاستضافة والطلبات والبيانات والنماذج والصيانة طوال دورة الحياة.
6. الاستدامة: تقليل الموارد والخدمات والعمليات غير الضرورية وإطالة عمر المكونات القابلة للصيانة.

يُجرى تقييم خفيف عند كل مرحلة معمارية كبرى، وتقييم أشمل قبل الإطلاق الإنتاجي أو تغيير قاعدة البيانات أو تقسيم النظام إلى خدمات. تُسجّل المخاطر وخطة معالجتها، ولا تتحول المراجعة إلى قائمة شكلية.

### 13.2 هندسة المتطلبات والتصميم قبل التنفيذ

- نبدأ من احتياج المستخدم وسيناريوهات الاستخدام، ثم نحدد المتطلبات الوظيفية وغير الوظيفية ومعايير القبول.
- نرسم حدود الوحدات ومسارات البيانات وحدود الثقة والتبعيات الخارجية قبل تغيير معماري واسع.
- نستخدم مخططات سياق/حاويات/مكونات بالقدر الذي يزيل الغموض، وADR لكل قرار تقني مؤثر.
- نسجل المفاضلات صراحة: البساطة مقابل المرونة، زمن التسليم مقابل مخاطر التغيير، الأداء مقابل التكلفة، والاستقلال مقابل تعقيد التشغيل.
- نمنع التوسع المبكر: لا microservices أو Kubernetes أو event streaming أو تعدد قواعد البيانات إلا عند وجود متطلب وقياس وخطة تشغيل تثبت الحاجة.
- كل واجهة بين وحدتين أو منتجين لها مالك وعقد واختبارات توافق وسياسة إهمال.

### 13.3 دورة تطوير وتسليم موثوقة (SDLC / CI/CD)

- تغييرات صغيرة، مستقلة، سهلة المراجعة والرجوع؛ لا نكدس إصلاحات وميزات وترقيات غير مترابطة في PR واحد.
- الفرع الرئيسي يبقى قابلاً للبناء والنشر، ويُحمى بقواعد Branch Protection وفحوص إلزامية ومراجعة حسب مستوى المخاطر. لا force-push أو حذف للفرع الرئيسي.
- كل PR يوضح المشكلة، الحل، الاختبارات، المخاطر، التوافق، الأثر على البيانات، وطريقة الرجوع.
- نؤتمت البناء والاختبارات والفحوص الأمنية، ونمنع الدمج عند فشل بوابة إلزامية أو غياب نتيجة فحص مطلوبة. لا نتجاوز الحماية لتسريع العمل.
- نفصل بيئات التطوير والاختبار/التجهيز والإنتاج، ولا نستخدم أسرار الإنتاج في CI أو الاختبارات.
- نبني artifact واحداً محدد الإصدار وبصمة المحتوى، ثم نرقّي artifact نفسه بين البيئات بدلاً من إعادة بنائه بمحتوى مختلف.
- تغييرات قاعدة البيانات تتبع نمط Expand → Migrate → Contract: توسعة متوافقة أولاً، نقل البيانات والتحقق، ثم إزالة القديم في إصدار لاحق بعد التأكد من عدم وجود مستهلكين.
- Feature flags أو النشر التدريجي أو canary تستخدم حين تدعمها البنية وتخفض المخاطر فعلاً؛ يجب أن يكون لكل flag مالك وتاريخ إزالة.
- اختبارات CI المتذبذبة (flaky) عيب يجب تشخيصه وإصلاحه، لا تعطيلها بصورة دائمة أو إعادة تشغيلها حتى تنجح بلا تفسير.

### 13.4 هندسة الاعتمادية وقياس تجربة المستخدم (SRE)

- نحدد لكل رحلة حرجة مؤشرات SLI مرتبطة بما يراه المستخدم، مثل نجاح تسجيل الدخول أو حفظ الرسالة أو إتمام إرسال الدرجة أو ترحيل المعاملة، وليس صحة الخادم وحدها.
- نختار SLO واقعياً بعد قياس خط أساس؛ لا نفرض نسبة توافر تسويقية قبل وجود قياس موثوق.
- عندما تصبح القياسات التشغيلية موثوقة، نستخدم Error Budget لتوجيه قرارات الإصدار: عند استهلاك الميزانية نؤجل التغييرات عالية المخاطر ونركز على الاعتمادية، مع استمرار إصلاحات الأمن والأعطال الحرجة.
- التنبيهات تكون على أعراض تؤثر على المستخدم أو تهدد SLO، وتُصنف إلى تنبيه فوري، أو مهمة متابعة، أو سجل تشخيصي.
- لكل خدمة حرجة Runbook يوضح الأعراض، الفحوص الأولية، حدود التصعيد، خطوات الاحتواء، الاستعادة، والتحقق بعد الإصلاح.
- الحوادث المهمة تُدار بسجل زمني واضح، وتوثق بتقرير Postmortem بلا لوم يركز على الأسباب النظامية والحواجز الوقائية.
- نختبر الاستعادة من النسخ الاحتياطية فعلياً، ونقيس RTO/RPO المحققين؛ وجود ملف backup أو نجاح مهمة النسخ لا يثبت قابلية الاستعادة.
- نعتمد التدهور المنضبط: عند تعطل خدمة غير أساسية، نحافظ على المسارات الأساسية أو نعرض حالة مفهومة بدلاً من انهيار النظام كله.

### 13.5 الأمن المدمج وسلسلة توريد البرمجيات (Secure SDLC)

نعتمد NIST SSDF مرجعاً لدورة التطوير الآمن، وOWASP ASVS مرجعاً لمتطلبات التحقق الأمني للتطبيقات، وOWASP SAMM لتقييم نضج الممارسات وتحسينها تدريجياً. خط الأساس الموثق حالياً هو NIST SP 800-218 SSDF 1.1 النهائي؛ نتابع مسودة 1.2 دون معاملتها كمعيار نهائي. إصدار OWASP ASVS المستقر المرجعي عند تحرير هذا الملحق هو 5.0.0.

بوابات الأمن المناسبة للمخاطر تشمل:
- Threat modeling قبل إضافة حدود ثقة أو تكامل خارجي أو صلاحيات أو معالجة ملفات/أوامر/مدفوعات/بيانات حساسة.
- مراجعة المصادقة والتفويض ورفض الوصول افتراضياً والتحقق من الملكية على الخادم، لا الاعتماد على إخفاء عناصر الواجهة.
- SAST وSCA وفحص الأسرار والحاويات والبنية التحتية عندما تنطبق؛ معالجة النتائج بحسب الخطورة وقابلية الاستغلال والسياق، مع توثيق الاستثناءات المؤقتة.
- تثبيت الإصدارات وملفات lock، وتقليل صلاحيات CI tokens وGitHub Actions، واستخدام إصدارات Actions مثبتة على SHA عند اعتماد ذلك، وعدم تمرير أسرار إلى عمليات غير موثوقة.
- إنشاء SBOM وبصمة/مصدر بناء موثوق للإصدارات الإنتاجية عندما تصبح عملية الإصدار جاهزة لذلك؛ لا ندعي وجودها قبل توليدها والتحقق منها.
- مراجعة تراخيص المكونات ومصادرها وصيانتها والثغرات المعروفة، ووضع سياسة لتحديثات الأمن الحرجة.
- حماية السجلات من الأسرار والرموز وبيانات المتعلمين والعملاء والمحتوى الخاص.
- اختبار التفويض السلبي، IDOR، CSRF، SSRF، XSS، حقن SQL/الأوامر، رفع الملفات، حدود المعدلات، وإدارة الجلسات بحسب سطح الهجوم الفعلي.
- لا تُستخدم بيانات المستخدمين الحقيقية في التطوير أو التدريب أو الاختبار إلا بتفويض وغرض واحتفاظ وضوابط خصوصية محددة.

### 13.6 الاختبارات كدليل جودة لا كعدد

- نربط كل متطلب أو خطر حرج باختبار يكشف فشله، ونغطي النجاح والفشل والحالات الطرفية والتزامن.
- نستخدم اختبارات Unit سريعة، ثم Contract/Component وIntegration، ثم E2E للتدفقات الأهم، واختبارات أمن وأداء وترحيل وفق المخاطر.
- نختبر التوافق بين إصدارات runtimes وقواعد البيانات والمتصفحات التي ندعمها فعلاً، لا كل تركيبة افتراضية.
- نستخدم بيانات اصطناعية قابلة لإعادة الإنتاج، وFixtures واضحة، وعزل بين الاختبارات، وتنظيفاً حتمياً للموارد.
- نختبر التزامن وسباقات الكتابة والعمليات المتكررة والمهلات وإعادة المحاولة وفقد الاتصال.
- كل مسار مالي أو درجات أو عزل شركات أو صلاحيات يحتاج اختبارات invariants واختبارات سلبية تمنع خرق الثوابت.
- نراقب flakiness ومدة الاختبارات والتغطية ذات القيمة؛ لا نطارد نسبة تغطية شكلية على حساب اختبارات المخاطر المهمة.
- إثبات E2E أو Sandbox أو استعادة البيانات يجب أن يتضمن البيئة والإصدار والتاريخ والنتيجة والدليل، لا مجرد عبارة «تم الاختبار».

### 13.7 المراقبة والتشخيص

نستخدم ثلاثة أنواع مترابطة من Telemetry:
- Metrics لقياس الاتجاهات والسعة وSLOs.
- Structured logs للأحداث التشخيصية مع مستوى وشكل ثابتين.
- Traces لتتبع الطلبات عبر حدود الخدمات حين توجد عدة خدمات أو تكاملات.

نربطها بمعرّف correlation/request، ونتجنب تسجيل محتوى الرسائل والملفات والرموز والبيانات الشخصية. يجب أن يستطيع الفريق الإجابة عن: ما الذي تعطل؟ من تأثر؟ متى بدأ؟ ما النسخة المتسببة؟ هل نجح التراجع؟ وهل عادت مؤشرات المستخدم إلى طبيعتها؟

### 13.8 قياس أداء التسليم دون إساءة استخدام الأرقام

عندما تتوفر بيانات كافية، نتابع مقاييس DORA الخمسة على مستوى المنتج/الخدمة:
1. Change lead time: من اعتماد التغيير في التحكم بالمصدر إلى وصوله للإنتاج.
2. Deployment frequency: معدل الإصدارات الناجحة.
3. Failed deployment recovery time: زمن التعافي من إصدار تسبب في تدهور.
4. Change fail rate: نسبة الإصدارات التي تحتاج تدخلاً فورياً.
5. Deployment rework rate: نسبة الإصدارات غير المخططة لإصلاح مشكلات إنتاجية.

تُستخدم المقاييس لتحسين سير العمل وتحديد الاختناقات، لا لترتيب الأفراد أو الضغط لزيادة النشر على حساب الجودة. نبدأ بخط أساس، ثم نختار اختناقاً واحداً للتحسين ونقيس النتيجة.

### 13.9 إدارة الأداء والتكلفة والسعة

- نضع ميزانية أداء للرحلات الحرجة: زمن الاستجابة، حجم الاستجابة، استهلاك الذاكرة، وعدد الاستعلامات أو الطلبات الخارجية.
- نستخدم profiling وقياساً قابلاً لإعادة الإنتاج قبل تحسينات الأداء؛ لا نضيف caching أو queues أو قواعد بيانات إضافية بلا قياس.
- نحدد حدود المعدلات والحصص وأحجام الملفات والوقت والذاكرة لكل عملية، مع حماية من إساءة الاستخدام.
- نراقب تكلفة الوحدة المناسبة: تكلفة المستخدم النشط أو الطلب أو الرسالة أو الشركة أو المهمة، بحسب المنتج.
- نفضل الخدمات المجانية أو منخفضة التكلفة الآن، ونراجع حدودها ومخاطر الاعتماد عليها وخطة الانتقال قبل اختيارها.
- أي هدف سعة كبير يحتاج workload موثقاً واختبارات load/stress/soak ونتائج محفوظة؛ لا تُستنتج السعة من عدد المستخدمين المسجلين فقط.

### 13.10 تجربة المطور وإدارة الدين التقني

- نوفر طريقة تشغيل محلية موحدة ومختصرة، وإعداداً مثالياً غير حساس، وتعليمات onboarding، وسكربتات فحص متكررة حيث تقلل الأخطاء.
- نوضح هيكل المجلدات وملكية الوحدات والاعتماديات واتفاقيات التسمية والتنسيق.
- نحتفظ بسجل Tech Debt يحدد السبب والأثر والأولوية وكلفة التأجيل وطريقة المعالجة؛ لا ندفن المخاطر في ملاحظات المحادثات.
- لا نعيد كتابة مكون يعمل لمجرد اختلاف الذوق. نحدد المشكلة والقياس وكلفة الترحيل أولاً.
- نزيل الشيفرة والاعتماديات والميزات القديمة بطريقة متدرجة بعد إثبات عدم استخدامها وخطة الرجوع.

### 13.11 مستويات التطبيق

يُطبق المعيار تدريجياً وفق نضج المنتج:
- **المستوى الأساسي الآن:** مستودع منظم، حماية الفروع حيث تسمح الصلاحيات، مراجعة PR، CI إلزامي، اختبارات Regression، إدارة الأسرار، توثيق القرارات، نسخ احتياطي واستعادة مثبتة، وسجل حالة واضح.
- **مستوى ما قبل الإنتاج:** Threat modeling، تحقق OWASP مناسب، SLO/SLI، Runbooks، اختبار حمل ونسخ/استعادة، Sandbox للتكاملات الخارجية، وفحوص سلسلة التوريد.
- **مستوى التوسع والإنتاج الحرج:** نشر تدريجي، Error Budgets، SBOM/provenance موثق، مراقبة موزعة، اختبارات مرونة وتعافٍ دورية، ومراجعات سعة وتكلفة دورية.

لا نؤجل الضوابط الأساسية بحجة أننا فريق صغير، ولا نفرض مستوى مؤسسي معقداً قبل الحاجة. نطبق أصغر مجموعة ضوابط فعالة تقلل المخاطر الحالية، ثم نرفع النضج مع نمو الاستخدام.
