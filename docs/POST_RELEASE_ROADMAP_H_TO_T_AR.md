# خارطة طريق ما بعد G — المراحل H إلى T

**المستودع:** `HVA09/ai-chat-app`  
**المرجع التنفيذي:** `main` هو مصدر الحقيقة الوحيد بعد دمج الوثيقة.  
**الحالة:** مسودة تنفيذية لتنظيم الخطة المستقبلية. المرحلة H هي الأولوية الحالية؛ المراحل I–T مخطط مبدئي يُراجع قبل بدء كل مرحلة.  
**آخر تحديث:** 2026-10-10

## لماذا أُنشئت هذه الوثيقة؟

خارطة الطريق الحالية `docs/AI_PLATFORM_ROADMAP_AR.md` توثّق المراحل السابقة حتى G والإصدار `v1.0.0`. راجعنا الملف الحالي وفروع المستودع وطلبات الدمج المتاحة، ولم نعثر على مواصفات موثقة كاملة ومتطابقة للمراحل H–T. لذلك فهذه الوثيقة **إعادة بناء منظمة للخطة المستقبلية بناءً على حالة المشروع والاتجاه المتفق عليه**، وليست ادعاءً بأن النص الحرفي للخطة القديمة قد استُرجع.

قبل تنفيذ أي مرحلة، يجب مطابقة نطاقها مع أحدث `main` وطلبات الدمج المفتوحة. أي وظيفة أُنجزت مسبقًا تُعامل باعتبارها وظيفة موجودة تحتاج إلى تحقق أو تحسين، لا ميزة تُعاد كتابتها.

## قواعد إلزامية لجميع المراحل

1. لا نبدأ مرحلة جديدة قبل إغلاق مشكلات الأولوية الأعلى أو توثيق قرار صريح بتأجيلها.
2. نراجع أحدث `main` والـPRs والاختبارات والملفات المتأثرة قبل الكتابة؛ لا نعتمد على ذاكرة المحادثة وحدها.
3. كل تغيير برمجي مستقل يعمل في فرع وPR منفصلين. لا يُدمج PR متعارض أو متجاوز أو مكرر.
4. لا تُعدّ الميزة مكتملة بسبب نجاح البناء فقط؛ نحتاج اختبارات مناسبة، وفحوص أمان، وتحققًا تشغيليًا عند انطباقه.
5. لا يُسمح بإضافة خدمة مدفوعة أو ترقية خطة أو إنشاء مورد يُحتمل أن يفرض تكلفة دون موافقة صريحة مسبقة.
6. لا نغيّر قاعدة الإنتاج أو الأسرار أو إعدادات النشر الحساسة اعتمادًا على التخمين. نتحقق من الحالة أولًا ونحافظ على إمكانية التراجع.
7. عند استخدام أكثر من جهاز، يجب أن يبدأ كل عمل من أحدث `main` وتُراجع الفروع المتزامنة لمنع التضارب وإعادة العمل.
8. تُحدّث هذه الوثيقة بعد كل مرحلة بذكر ما تغيّر فعلًا، والـPR والـcommit ونتائج CI/CodeQL والتشغيل، وما بقي.
9. لا تُثبّت تفاصيل المراحل البعيدة نهائيًا إذا أظهر الاستخدام أو نتائج القياس أن الأولويات يجب أن تتغير.

## I — تجربة الهاتف، قابلية الاستخدام وإمكانية الوصول

**الهدف:** أن تكون التجربة اليومية واضحة وعملية على شاشة صغيرة، دون إفساد تجربة سطح المكتب.

### الأعمال
- إعادة اختبار القائمة الجانبية وزر فتحها وإغلاقها على هاتف حقيقي.
- اختبار رفع الملفات وظهور المرفقات والوصول إلى زر الإرسال دون أن تغطيه لوحة المفاتيح أو عناصر الواجهة.
- ضبط أحجام النصوص والمسافات وعرض الرسائل لتكون قابلة للقراءة وغير ضخمة.
- تسهيل الوصول إلى الصوت والميكروفون والوظائف المستخدمة كثيرًا.
- مراجعة مكان الإعدادات وتقليل القوائم والإجراءات غير الضرورية مع الحفاظ على سهولة اكتشاف الوظائف الأساسية.
- التحقق من العربية والإنجليزية واتجاه RTL/LTR وحالات التحميل والخطأ والفراغ والتركيز والتنقل بلوحة المفاتيح حيث ينطبق.
- إضافة اختبارات انحدار للمشكلات التي يمكن تمثيلها آليًا.

### بوابة الإغلاق
- قائمة قبول يدوية موثقة على الهاتف، مع نتيجة لكل حالة.
- اجتياز اختبارات الواجهة والبناء.
- لا يُعلن حل عطل مبلّغ عنه قبل إعادة إنتاجه ثم اختبار إصلاحه.

## J — تنظيم المعمارية وقابلية صيانة الواجهة

**الهدف:** جعل الشيفرة أسهل قراءة واختبارًا وتطويرًا دون إعادة كتابة شاملة غير ضرورية.

### الأعمال
- قياس الأجزاء التي لا تزال متضخمة في `App.jsx` بعد مراجعة الـhooks التي وصلت فعلًا إلى `main`.
- فصل السلوكيات إلى hooks أو وحدات واضحة عند وجود حدود مسؤولية حقيقية، مع إبقاء المكونات المرئية ومصادر الحالة مفهومة.
- مراجعة ترتيب اعتماد الـhooks وتأثيراتها وإدارة دورة حياة البيانات والاشتراكات والتعامل مع الإلغاء وإعادة المحاولة.
- إزالة الاستيرادات أو الحالات أو المسارات المكررة التي يثبت أنها غير مستخدمة؛ لا نحذف اعتمادًا على التخمين.
- الحفاظ على سلوك الرسائل والمحادثات والإشعارات والصوت ومشاركة المحادثات أثناء التفكيك المعماري.

### بوابة الإغلاق
- اختبارات سلوكية مركزة لكل وحدة مفصولة.
- عدم وجود تراجع في حالات النجاح أو الفشل أو استرجاع الحالة (rollback).
- لا يتضخم عدد الملفات والوحدات دون تحسن واضح في حدود المسؤولية.

## K — الأداء والاستجابة واستهلاك الموارد

**الهدف:** قياس نقاط البطء ثم معالجة الأسباب المثبتة.

### الأعمال
- تحديد خط أساس لحجم حزمة الواجهة وزمن التحميل والتفاعل وإعادة التصيير، بدل الادعاء بأن التطبيق أصبح أسرع دون قياس.
- فحص القوائم الطويلة والمحادثات الكبيرة والمرفقات والمعاينة والمحرر.
- مراجعة طلبات API المتكررة وجلب البيانات والتخزين المؤقت والعمليات التي يمكن إلغاؤها عند تغيير الصفحة أو المحادثة.
- قياس أزمنة نقاط النهاية المهمة وسلوك بدء الخدمة المجانية، مع التمييز بين بطء الإقلاع وبطء التطبيق.
- تحسين الأداء فقط حيث تظهر القياسات فائدة، مع الحفاظ على حدود الذاكرة وحجم الملفات والمهل.

### بوابة الإغلاق
- نتائج قبل/بعد قابلة للمقارنة على سيناريوهات محددة.
- لا كسر في الوظائف ولا زيادة غير مبررة في الموارد أو التكلفة.

## L — صقل المحادثة والوظائف متعددة الوسائط

**الهدف:** جعل مسارات المحادثة الموجودة أكثر اتساقًا ووضوحًا.

### الأعمال
- تدقيق دورة إرسال الرسالة والبث وعرض حالة التشغيل والأخطاء والإلغاء.
- اختبار إعادة التوليد وتعديل الرسائل وتفريع المحادثة والحذف والمشاركة والاستيراد والتصدير وفق التنفيذ الموجود حاليًا.
- اختبار الصور والمرفقات والصوت وحالات فشل المعالجة وإمكانية إعادة المحاولة دون تكرار الرسائل.
- توحيد حالات الواجهة: جارٍ الإرسال، جارٍ التحليل، اكتمل، فشل، أُلغي، أو يحتاج إلى إعادة المحاولة.
- التأكد من بقاء الرسائل المتفائلة متسقة عند فشل API ومن عدم فقدان المحتوى بصمت.

### بوابة الإغلاق
- اختبارات للمسارات الأساسية والحدية وفشل الطلبات.
- لا يُعاد بناء سلوك موجود إذا كان المطلوب مجرد إصلاح أو تحسين موضعي.

## M — جودة الملفات والمعرفة وRAG

**الهدف:** تحسين موثوقية الإجابات المعتمدة على الملفات والبيانات وقياس الجودة بدل الاكتفاء بوجود خط المعالجة.

### الأعمال
- مراجعة دورة الملف من الرفع إلى المعالجة والفهرسة وإتاحة البحث، مع حالات واضحة للانتظار والجاهزية والفشل.
- فحص سلامة إعادة المحاولة ومنع الفهرسة المكررة وسلامة الحذف وتغيير الملف.
- بناء مجموعة تقييم صغيرة ومنضبطة لأسئلة الملفات وصحة الاسترجاع وملاءمة المقاطع والمصادر.
- التحقق من عزل الملفات والمقاطع بين المستخدمين والمشاريع ومساحات العمل.
- عرض المصادر وحدود المعرفة وعدم اختلاق إجابة عندما لا تتوفر أدلة كافية.
- مراجعة التكلفة والحصص قبل أي توسعة لخط معالجة الملفات أو embeddings.

### بوابة الإغلاق
- اختبارات دورة حياة الملفات والعزل والأخطاء.
- نتائج تقييم قابلة للتكرار مع توثيق حدود الدقة المعروفة.
- عدم إدخال مخزن أو مزود مدفوع دون موافقة.

## N — تحسين Agent وProject Builder

**الهدف:** توسيع مسارات العمل الذكي بصورة آمنة فوق البنية الموجودة.

### الأعمال
- اختبار رحلة المشروع كاملة: الملفات والتحرير والتعاون والتحقق وخطة المعاينة والبناء والعرض والاستيراد والتصدير.
- التأكد من أن فشل البناء لا يفسد ملفات المشروع وأن التعارضات تظهر للمستخدم بوضوح.
- اختبار checkpoints وإعادة المحاولة والإيقاف والاستئناف والإلغاء لمهام Agent.
- حماية حدود الوقت والتكلفة وعدد الأدوات وحجم مخرجاتها.
- مراجعة عزل Builder والمعاينة والرموز المؤقتة وسياسات CSP قبل إضافة أي نوع مشروع أو تشغيل.
- تحسين رسائل المستخدم عند رفض تعديل غير آمن أو وجود تعارض في الملف.

### بوابة الإغلاق
- اختبارات كاملة لمسارات النجاح والفشل والاستئناف والعزل.
- اختبار فعلي للمشروع والمعاينة عند انطباقه، دون تشغيل كود غير موثوق داخل origin التطبيق الأساسي.
- لا موارد مدفوعة جديدة.

## O — تعاون Workspace والمشاركة والصلاحيات

**الهدف:** تحسين تجربة الفرق والمشاركة فوق آليات العضوية والأدوار الموجودة.

### الأعمال

- حسم التغييرات المفتوحة المرتبطة بمشاركة محادثات Workspace بعد حل التعارضات.
- اختبار الاتساق بين صلاحيات الواجهة وفحوص الصلاحية في Backend.
- تحسين رسائل الأخطاء وحالات الدعوة المنتهية أو غير الصالحة وإزالة العضوية.
- توثيق أثر أي عملية جماعية أو تغيير صلاحيات حساس.

### بوابة الإغلاق
- اختبارات cross-user وrole-based على المسارات التي تتغير.
- لا يعتمد الأمان على إخفاء زر في الواجهة.

## P — نضج منظومة المطورين وDeveloper API

**الهدف:** تحسين سهولة التكامل والتوافق مع الحفاظ على القدرات الموجودة في API v1 والمفاتيح والـwebhooks والـSDKs وOAuth.

### الأعمال

- تحسين أمثلة البدء السريع والأخطاء وحدود المعدلات و`X-Request-ID` وسلوك إعادة المحاولة.
- إضافة اختبارات توافق للعقد عند تعديل المسارات أو أنواع البيانات.
- تحسين وضوح إدارة المفاتيح وإلغائها والاستهلاك وإعداد webhooks والتكاملات.
- عدم إنشاء API أو SDK ثانٍ لوظيفة موجودة؛ أي تغيير كاسر يحتاج إصدارًا رئيسيًا جديدًا.

### بوابة الإغلاق
- اختبارات عقد API وSDK متوافقة وموثقة.
- أمثلة قابلة للتشغيل في بيئة مجانية أو محلية حيثما أمكن.
