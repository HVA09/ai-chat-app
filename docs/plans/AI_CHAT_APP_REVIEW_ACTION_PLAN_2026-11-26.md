# خطة المهام والتوصيات الناتجة عن مراجعات AI Chat App

- التاريخ: 2026-11-26
- المستودع: `HVA09/ai-chat-app`
- الفرع المرجعي عند إعداد المراجعات: `main`
- SHA المرجعي الوارد في سجلات المراجعة: `a40c50fce7dd1e531a8cbed5501206418dc66908`
- النطاق: AI Chat App فقط. هذه الخطة لا تشمل Lumen أو ERP أو AI Core.
- طبيعة الأدلة: مراجعات مصدرية وتقارير CI سابقة. البنود أدناه ليست ادعاءً بأن الإصلاحات نُفذت أو أن الإنتاج اختُبر. يجب إعادة التحقق من كل finding على HEAD الحالي قبل التنفيذ.

## 1. قواعد التنفيذ والحماية

1. الحفاظ على `main` مستقراً؛ تنفيذ التغييرات عبر فروع قصيرة وPull Requests منفصلة حسب المجال.
2. عدم دمج أي PR قبل نجاح الفحوص المطلوبة، ومراجعة diff، والتحقق من الصلاحيات والبيانات، وقبول معايير القبول.
3. عدم تشغيل Workers أو Beat أو Schedulers أو Cleanup/Reconciliation workers خلال مرحلة التدقيق أو قبل اعتماد تصميم تشغيل آمن.
4. عدم تنفيذ migrations أو تغييرات على Production أو Supabase أو Object Storage أو الأسرار دون خطة تغيير واختبار واستعادة موثق.
5. عدم اعتبار مراجعة المصدر أو نجاح `pg_restore --list` إثباتاً لنجاح استعادة فعلية.
6. عدم إضافة CI مكرر؛ البناء الحالي يتضمن بالفعل اختبارات Backend وFrontend وSDK، وفحوص migrations/ORM، وCodeQL وبناء Docker وProduction smoke بحسب سجلات CI التي راجعتها المراجعة.
7. استخدام أقل صلاحيات ممكنة، والحفاظ على فصل بيانات المستخدمين والمشاريع ومساحات العمل.
8. قياس الأداء قبل إضافة فهارس أو Virtualization أو تغييرات واسعة.
9. أي سلوك غير مثبت تشغيلياً يبقى موسوماً «يحتاج اختباراً» ولا يوصف بأنه حادث إنتاج مؤكد.

## 2. قائمة المهام حسب الأولوية

### P0 — لا يوجد بند P0 مثبت في هذه المراجعات

لا توجد نتيجة موثقة هنا تبرر إعلان حادث P0 أو إجراء تغيير طارئ على الإنتاج.

### P1 — أمن البيانات وموثوقية الوظائف الأساسية

#### P1-01 — فرض صلاحيات المشروع الحالية أثناء تصدير الحساب
- المجال: تصدير البيانات والخصوصية.
- الملاحظة: استعلام ذاكرة المشروع في مسار التصدير يعتمد على منشئ الذاكرة، ولا يثبت وحده استمرار عضوية/صلاحية المستخدم في المشروع.
- المهمة: تطبيق فحص ACL الحالي نفسه المستخدم في واجهات المشروع قبل إدراج أي ذاكرة أو بيانات مشروع في التصدير.
- القبول: مستخدم أزيلت عضويته لا يستطيع تصدير ذاكرة المشروع؛ مالك/عضو مخول يستطيع تصدير ما تسمح به صلاحياته؛ اختبارات cross-user وrevoked-membership.

#### P1-02 — سلامة علاقات المستأجر المركبة
- المجال: PostgreSQL / ORM / Multi-tenancy.
- الملاحظة: بعض العلاقات تستخدم مفاتيح أجنبية منفصلة لـ workspace وproject ولا تضمن وحدها تطابق نطاق الملكية.
- المهمة: حصر العلاقات المتأثرة ودراسة Composite Foreign Keys أو قيود مكافئة تضمن أن المشروع والمحادثة والملف ينتمون إلى مساحة العمل/المستأجر الصحيح.
- القبول: اختبارات DB ترفض العلاقات المتقاطعة بين مساحات عمل مختلفة؛ migrations قابلة للتراجع؛ لا تكسر مسارات المشاركة والحذف الحالية.

#### P1-03 — منع تقديم نسخة محلية قديمة عند فشل S3
- المجال: Object Storage.
- الملاحظة: fallback المحلي في قراءة الملفات قد يعمل عند أخطاء S3 أوسع من حالة عدم وجود الكائن.
- المهمة: التفريق بين NotFound وAccessDenied والمصادقة وأخطاء الشبكة و5xx؛ لا تستخدم النسخة المحلية إلا وفق سياسة صريحة تثبت أنها authoritative ومتوافقة.
- القبول: AccessDenied/Network/5xx لا تتحول بصمت إلى نسخة محلية قديمة؛ NotFound له سلوك موثق؛ اختبارات لكل فئة خطأ.

#### P1-04 — وضع حدود للقراءة والنسخ من Object Storage
- المجال: التخزين والموارد.
- الملاحظة: `get_bytes()` يقرأ Body كاملاً، ولا يظهر حد مستقل موحد؛ ونسخ الملفات المؤقتة يحتاج سقفاً أثناء النقل وإغلاقاً مضموناً للـ Body.
- المهمة: إضافة حدود حجم/زمن للقراءة والنسخ، streaming عند الحاجة، إغلاق response body في finally/context manager، وتنظيف الملفات الجزئية.
- القبول: ملفات فوق الحد ترفض برسالة متوقعة؛ لا تسريب لمقابض الملفات؛ اختبارات انقطاع النقل والتنظيف.

#### P1-05 — توحيد التحقق من Object Keys
- المجال: أمن التخزين.
- الملاحظة: التحقق من المسارات غير متسق بين put/get/open/delete/materialize.
- المهمة: validator مركزي لجميع عمليات التخزين، يرفض المسارات المطلقة والمقاطع النسبية والمفاتيح خارج نطاق المستخدم/المستأجر.
- القبول: الاختبارات تغطي كل عمليات القراءة والكتابة والحذف والمفاتيح المشوهة؛ لا توجد دالة تتجاوز validator.

#### P1-06 — معالجة انتهاء SSE دون حدث نهائي
- المجال: Chat Streaming.
- الملاحظة: مسار الدردشة العادي قد ينتهي قبل `done` دون تحويل الحالة بوضوح إلى فشل؛ مسار Agent لديه تحقق مختلف.
- المهمة: اعتبار `done` أو حدث نهائي معتمد شرطاً لإكمال البث؛ انتهاء الجسم قبل الحدث النهائي خطأ نقل/بروتوكول، مع تنظيف حالة الواجهة.
- القبول: اختبارات لكل من Chat/Regenerate/Edit/Agent عند EOF قبل done؛ تظهر حالة خطأ قابلة لإعادة المحاولة ولا تبقى الواجهة في Loading.

#### P1-07 — فصل الإيقاف عن الاكتمال
- المجال: SSE / Stop Generation.
- الملاحظة: AbortError في بعض مسارات الواجهة يعامل كـ onDone، بينما الإيقاف قد يترك رسالة مستخدم محفوظة دون رد مساعد.
- المهمة: اعتماد حالات منفصلة مثل completed/stopped/failed/timed_out، وعرضها بوضوح؛ لا يوصف الإيقاف بأنه اكتمال ناجح.
- القبول: اختبار إيقاف قبل أول token وأثناء البث وبعده؛ لا يكرر رسالة المستخدم؛ لا يحفظ رد مساعد جزئياً كأنه مكتمل.

#### P1-08 — Idempotency لطلبات إرسال الرسائل
- المجال: Chat API / DB.
- الملاحظة: نجاح retry/regenerate في منع تكرار رسالة المستخدم لا يثبت منع تكرار POST الأصلي عند إعادة الإرسال بعد انقطاع الشبكة.
- المهمة: تصميم Idempotency Key لكل عملية إرسال، مع قيد فريد ونطاق ملكية واضح ونتيجة قابلة لإعادة القراءة.
- القبول: إرسال الطلب نفسه مرتين ينتج رسالة/عملية واحدة؛ مفاتيح مستخدمين مختلفين لا تتصادم؛ اختبارات timeout ثم retry.

#### P1-09 — تنسيق الطلبات المتزامنة للمحادثة
- المجال: سلامة سجل المحادثة.
- الملاحظة: يمكن لطلبين متزامنين بناء التاريخ نفسه وإكمال الردود بترتيب مختلف؛ ترتيب التاريخ يحتاج مفتاحاً ثانوياً ثابتاً.
- المهمة: اعتماد ترتيب `(created_at, id)` في جميع المسارات، ودراسة conversation version/lock أو آلية تسلسل مناسبة تمنع اعتماد رد على تاريخ قديم دون كشف التعارض.
- القبول: اختبارات concurrent sends/edit/delete/regenerate؛ ترتيب ثابت؛ لا ردود يتيمة أو مكررة أو مربوطة بمحادثة خاطئة.

#### P1-10 — إصلاح تبديل المحادثات في الواجهة
- المجال: Frontend UX / data integrity.
- الملاحظة: يتغير conversationId قبل استبدال messages، وقد تبقى رسائل المحادثة السابقة أثناء انتظار بيانات ثانوية.
- المهمة: ربط الرسائل بمعرف المحادثة، وإظهار loading/empty state عند التبديل، وتحديث الرسائل بمجرد وصول تفاصيل المحادثة الصحيحة دون انتظار بيانات ثانوية غير لازمة.
- القبول: لا تظهر رسالة من محادثة A تحت معرف B في أي توقيت؛ الاستجابات القديمة لا تستبدل الحالة الجديدة؛ اختبارات تبديل سريع بين عدة محادثات.

#### P1-11 — إغلاق القائمة الجانبية بعد اختيار محادثة على الهاتف
- المجال: Mobile UX.
- الملاحظة: مسار اختيار محادثة في SidebarModern لا يغلق mobile menu صراحة كما يفعل مسار المحادثة الجديدة.
- المهمة: إغلاق القائمة بعد الاختيار الناجح، مع الحفاظ على سلوك لوحة المفاتيح والتركيز.
- القبول: اختبار شاشة هاتف يثبت إغلاق القائمة وظهور المحادثة المختارة.

#### P1-12 — تجديد الجلسة في SSE
- المجال: Authentication / API integration.
- الملاحظة: Axios interceptor يجدد الجلسة لطلبات REST، بينما Fetch المباشر في SSE لا يستفيد من المسار نفسه.
- المهمة: طبقة موحدة لبدء SSE تدعم تجديداً مضبوطاً مرة واحدة عند 401، وتمنع تكرار عمليات الإرسال ذات الآثار الجانبية؛ إعادة طلب Agent تحتاج حماية خاصة.
- القبول: Access token منتهي مع Refresh صالح لا يسبب logout غير ضروري؛ refresh متزامن لا ينشئ سباقاً؛ لا تكرار لإرسال الرسالة أو تنفيذ الأدوات.

#### P1-13 — إصلاح صلاحيات الملفات ونتائج Agent
- المجال: RBAC / Project ACL.
- الملاحظة: مراجعات سابقة أشارت إلى ضرورة إعادة فحص صلاحية المستخدم عند الوصول للملفات/نتائج Agent وبعد تغيّر العضوية.
- المهمة: إعادة التحقق من ACL عند كل read/download/RAG retrieval، وإعادة فحص ملكية/عضوية المشروع قبل حفظ أو إرجاع نتائج Agent؛ توحيد صلاحية `projects.manage` بدلاً من فحوص أدوار قديمة.
- القبول: إزالة العضوية أثناء العملية تمنع الوصول اللاحق؛ اختبارات cross-tenant وrevoked membership وملفات Image-RAG؛ لا تعتمد النتائج على فحص قديم فقط.

#### P1-14 — فصل migrations عن بدء خدمة API
- المجال: Release / Database operations.
- الملاحظة: `start.sh` يشغل `alembic upgrade head` عند بدء الخدمة.
- المهمة: نقل migration إلى خطوة release منفصلة ومحكومة، وتوثيق نمط expand/contract وتوافق الإصدار السابق.
- القبول: بدء API لا ينفذ migrations؛ نشر نسختين متوافقتين مع schema خلال الانتقال؛ اختبار فشل migration وخطة rollback.

#### P1-15 — موثوقية النسخ الاحتياطية والاستعادة
- المجال: Disaster Recovery.
- المهمة: إضافة SHA-256 مستقل محفوظ ومتحقق منه بعد الرفع؛ توثيق retention؛ تحديد نطاق نسخ DB وObject Storage والملفات؛ إجراء restore drill معزول إلى staging مع تحقق وظيفي وبيانات.
- القبول: استعادة كاملة ناجحة موثقة؛ تحقق checksum؛ قياس RPO/RTO؛ لا استعادة إلى Production من workflow staging؛ اختبار استعادة الملفات والعلاقات وليس اتصال SELECT 1 فقط.

#### P1-16 — منع فقدان المهام بسبب Redis غير الدائم
- المجال: Infrastructure / Celery.
- الملاحظة: إعداد Redis الوارد في المراجعة غير دائم ويستخدم `allkeys-lru`، بينما Redis يخدم عدة أدوار.
- المهمة: تقييم فصل Cache عن Broker/Queue، وسياسة durability/ack/retry/dead-letter المناسبة. لا تفعّل Workers أو Beat خلال التقييم.
- القبول: تصميم موثق يوضح سلوك فقد Redis وإعادة التشغيل والمهام المكررة؛ اختبار staging قبل أي تغيير إنتاجي.

#### P1-17 — فصل Liveness عن Readiness
- المجال: Operations.
- الملاحظة: Render health check يستخدم `/health` بينما `/ready` يفحص PostgreSQL وRedis.
- المهمة: تعريف Liveness وReadiness وفحوص الاعتماديات الاختيارية/الإلزامية، وضبط الاستضافة بحيث لا تسبب تبعية اختيارية restart غير لازم.
- القبول: سيناريوهات DB/Redis down تعطي حالات صحيحة؛ لا restart loop بسبب فشل خدمة اختيارية؛ توثيق ما يعنيه كل endpoint.

#### P1-18 — حساب الحد الأقصى لاتصالات PostgreSQL
- المجال: Capacity.
- المهمة: حساب إجمالي اتصالات API وWorker وBeat والنسخ المتعددة وعمليات المهام، ومقارنته بحد PostgreSQL/Pooler.
- القبول: ورقة حساب واختبار ضغط محدود يثبت عدم استنزاف الاتصالات؛ لا زيادة Pool قبل القياس.

#### P1-19 — عدم تشغيل Celery/Beat/Scheduler ضمن الإعداد غير المعتمد
- المجال: Deployment safety.
- الملاحظة: `render.yaml` يضبط `EMBEDDED_CELERY=true`، و`start.sh` يبدأ Worker وBeat عند التفعيل؛ Beat يرسل مهمة دورية كل 60 ثانية.
- المهمة: مراجعة التصميم والتكوين وتحديد قرار تشغيل منفصل؛ إبقاء التشغيل معطلاً خلال التدقيق وعدم تفعيل Cleanup/Reconciler قبل إثبات شروط الملكية والتوقف.
- القبول: لا Worker/Beat مضمّن غير مقصود؛ تشغيل المهام منفصل ومراقب ومعتمد؛ لا تشغيل تلقائي بسبب قيمة Blueprint غير متوقعة.

### P2 — تحسينات الجودة والأداء والتشغيل

#### P2-01 — SSE Heartbeat ومواءمة المهل
- المهمة: توحيد إعدادات Provider timeout وidle timeout وproxy timeout، وإضافة SSE keepalive عند الحاجة.
- القبول: لا انقطاع لاتصال خامل مشروع؛ timeout الحقيقي ينتهي بوضوح؛ لا انتظار غير محدود.

#### P2-02 — توحيد SSE Parser
- المهمة: دمج Chat/Regenerate/Edit في parser مشترك يدعم CRLF وتعدد data lines وUTF-8 المجزأ والأحداث النهائية.
- القبول: اختبارات chunk boundaries وUnicode وEOF وevent ordering؛ لا اختلاف غير مقصود بين المسارات.

#### P2-03 — WebSocket reconnect ومزامنة الإشعارات
- المهمة: إعادة اتصال تدريجية مع backoff، ثم مزامنة الإشعارات الفائتة من API.
- القبول: قطع الشبكة وإعادتها لا يفقد الإشعارات ولا ينشئ اتصالات متكررة بلا حد.

#### P2-04 — تحسين أداء الرسائل الطويلة
- المهمة: استخدام message ID ثابت بدلاً من index، وعزل الرسائل الثابتة عن الرسالة المتدفقة، وقياس إعادة العرض؛ تقييم virtualization فقط بعد القياس.
- القبول: benchmark لمحادثات طويلة؛ انخفاض rerenders دون كسر التمرير أو تحديد النص أو إجراءات الرسائل.

#### P2-05 — توحيد Object Key وFile Download lifecycle
- المهمة: توحيد تنزيل الملفات وإدارة Blob URL وعدم إلغائه قبل اكتمال الاستخدام.
- القبول: اختبارات Browser على تنزيل ملفات كبيرة وصغيرة على Android/desktop.

#### P2-06 — Pagination contract
- المهمة: اعتماد استجابة موحدة تتضمن items وtotal/has_more أو cursor، مع الحفاظ على التوافق الخلفي.
- القبول: pagination لا تكرر أو تتخطى عناصر عند التحديثات المتزامنة.

#### P2-07 — E2E للمتصفح والهاتف
- المهمة: إضافة مجموعة E2E خفيفة مجانية تغطي تسجيل الدخول، تبديل المحادثات، إرسال/إيقاف/إعادة المحاولة، الملفات، Sidebar، تنزيل الملف، RTL وmobile viewport.
- القبول: تعمل في CI على بيئة اختبار؛ لا تستخدم بيانات إنتاجية أو أسراراً حقيقية.

#### P2-08 — تثبيت اعتماديات Frontend
- المهمة: إضافة lockfile موثوق والتحول إلى `npm ci` في CI والبناء.
- القبول: تثبيت reproducible؛ lockfile متزامن مع package manifest؛ لا اعتماد على `npm install` غير الحتمي في CI.

#### P2-09 — فهرسة PostgreSQL بناءً على القياس
- المهمة: تحليل الاستعلامات الأكثر استخداماً وخططها قبل إضافة فهارس مركبة.
- القبول: EXPLAIN/ANALYZE في staging على بيانات ممثلة؛ إثبات تحسن دون كلفة كتابة غير مبررة.

#### P2-10 — مراقبة Queue وDependencies
- المهمة: مراقبة Queue depth/age، المهام الفاشلة، DB pool exhaustion، Redis memory/evictions، AI provider latency/failure rate، Worker/Beat liveness.
- القبول: لوحات وتنبيهات قابلة للاختبار مع runbooks؛ عدم كشف بيانات أو أسرار في metrics/logs.

#### P2-11 — توحيد CI دون تكرار
- المهمة: الإبقاء على workflows الحالية وإضافة اختبارات الفجوات أعلاه فقط؛ تقييم `npm ci` وcoverage gate وE2E.
- القبول: لا workflow مكرر؛ required checks واضحة؛ فشل الاختبار الجديد يمنع الدمج.

#### P2-12 — اختبارات Parser وتزامن الواجهة
- المهمة: تغطية CRLF وmulti-line data وUTF-8 boundaries، وتزامن edit/delete/regenerate/send، وحالات الرد القديم بعد طلب أحدث.
- القبول: اختبارات حتمية بلا اعتماد على timing هش.

#### P2-13 — سياسات الاحتفاظ والقياس
- المهمة: توثيق retention للنسخ والملفات والبيانات المؤقتة، وربط ذلك بمتطلبات الخصوصية والاستعادة.
- القبول: جدول retention واضح، واختبارات تثبت الحذف/الاحتفاظ وفق السياسة.

## 5. البنود التي تحتاج إعادة تحقق قبل اعتمادها كعيوب مؤكدة

هذه الملاحظات وردت في المراجعات المصدرية، ويجب إعادة فحصها على HEAD الحالي أو في بيئة staging قبل تحويلها إلى إصلاحات مؤكدة:
- عدم اتساق fallback المحلي مع أنواع أخطاء S3.
- حدود حجم القراءة والنسخ وإغلاق Body في جميع المسارات.
- سلوك إلغاء HTTPX عند إلغاء العميل في جميع حالات المزود.
- توقيت إلغاء Blob URL عبر المتصفحات.
- التداخل البصري لقواعد CSS على أحجام الهاتف.
- الأداء الفعلي لإعادة عرض الرسائل الطويلة.
- حالة Worker/Beat الحية؛ ملفات Blueprint تثبت التكوين لا الحالة الحية.
- تطبيق RLS الفعلي في Production؛ الترحيلات تثبت النية/التكوين لا حالة قاعدة البيانات الحية.
- نجاح استعادة backup كاملة؛ فحص الأرشيف لا يثبت الاستعادة.

## 6. خارج النطاق

- لا تغييرات على Lumen أو ERP أو أي مستودع آخر.
- لا إضافة مزود AI أو ميزات منتج جديدة ضمن هذه الخطة.
- لا نشر أو تعديل إعدادات Production أثناء مرحلة التوثيق.
- لا تشغيل Celery/Beat/Scheduler/Cleanup Worker قبل اعتماد خطة تشغيل واختبار.
- لا تنفيذ migrations على Production.
- لا حذف بيانات أو ملفات أو أسرار.
