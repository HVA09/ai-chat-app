# تقييم قدرات المساعد التقني المتخصص

**الحالة:** مواصفة تقييم أولية — لم تُشغّل بعد على النموذج، ولا تمثل ادعاءً بأن القدرات تحققت.  
**الهدف:** قياس الأداء قبل إضافة المعرفة والأدوات، ثم مقارنة النتائج بعد كل مرحلة تطوير.  
**المبدأ:** نقيّم المخرجات الفعلية لا وجود الكود أو جودة الوصف فقط.

## 1. ما الذي يجب أن نقيسه؟

1. **الصحة الفنية:** هل الإجابة دقيقة ومناسبة للإصدار والسياق؟
2. **الاكتمال:** هل غطت المتطلبات والقيود والحالات المهمة؟
3. **قابلية التحقق:** هل تستند إلى مصدر موثوق أو اختبار/مخرجات أداة عند الحاجة؟
4. **الشرح والتعليم:** هل الشرح واضح ومناسب لمستوى المتعلم، وهل يشرح الأخطاء بدل تقديم الحل فقط؟
5. **التنفيذ:** إذا أنتجت المهمة كودًا أو إعدادات، هل نجحت الاختبارات أو تحقق التكوين؟
6. **الأمان:** هل تحترم الصلاحيات، وتحمي الأسرار، وتفرق بين مختبر مصرح به ونظام غير مصرح باختباره؟
7. **الصدق بشأن الأدوات:** هل تميز بين اقتراح أمر وبين تشغيله فعليًا؟ لا تُمنح نقاط على ادعاء تنفيذ غير مدعوم بدليل.
8. **الربط بين المجالات:** هل الحل المتكامل متناسق، أم أن أجزاء الشبكة والنظام والبرنامج والسحابة تتعارض؟

## 2. مجموعة الاختبار الأولية

ابدأ بمجموعات صغيرة يسهل مراجعتها يدويًا. لكل مهمة يجب حفظ: المعرّف، نص السؤال، السياق/القيود، الإجابة المرجعية أو عناصر التقييم، إصدار النموذج، التاريخ، المخرجات، الأدلة، الدرجة، وسبب أي إخفاق.

### A. الشبكات

- تفسير عنوان IPv4 وتقسيم شبكة إلى شبكات فرعية وفق عدد الأجهزة المطلوب.
- تشخيص فشل DNS من نتائج `dig` أو `nslookup` مقدمة في السؤال.
- تحليل سبب عدم الوصول بين VLANs اعتمادًا على جدول routing وACL مرفق.
- اقتراح خطوات آمنة لتشخيص TCP/HTTPS دون ادعاء إجراء فحص لم يحدث.
- تصميم شبكة سحابية من subnets ومسارات وحدود أمان مع تبرير القرارات.

### B. Linux وإدارة الأنظمة

- تفسير مخرجات `systemctl` و`journalctl` وتحديد الخطوة التالية.
- تشخيص مشكلة صلاحيات ملف أو مجلد دون اقتراح صلاحيات مفرطة مثل `777` كحل افتراضي.
- كتابة Bash script مع تحقق من المدخلات، ومعالجة الأخطاء، ووضع اختبار قابل للإعادة.
- تحليل امتلاء القرص من `df` و`du` وبيانات السجلات، دون حذف عشوائي.
- إعداد خدمة Linux بأسلوب آمن وشرح كيفية التحقق والتراجع.

### C. البرمجة وهندسة البرمجيات

- كتابة دالة Python تتعامل مع حالات حدية واختبارات واضحة.
- تشخيص traceback مقدّم، وتحديد السبب والجذر والإصلاح دون اختلاق تشغيل.
- تنفيذ endpoint بسيط مع validation ومعالجة أخطاء واختبارات.
- مراجعة كود لاكتشاف أخطاء منطقية أو مشكلات أمنية، ثم تقديم patch صغير.
- تصميم تغيير قابل للصيانة مع خطة ترحيل/توافق واختبارات regression عند الحاجة.

### D. الأمن السيبراني

- اكتشاف إعداد ضعيف من تكوين تجريبي، وشرح الخطر وإجراء المعالجة.
- تحليل سجلات دخول/شبكة افتراضية وتقديم فرضيات مرتبة حسب الأدلة.
- مراجعة API لمشكلات المصادقة والتفويض والتحقق من المدخلات وإدارة الأسرار.
- كتابة قائمة hardening لخادم Linux أو قاعدة بيانات مع ترتيب المخاطر.
- حل سيناريو استجابة لحادث دفاعي مع احتواء وجمع أدلة واستعادة، ضمن بيئة يملكها المستخدم أو لديه تصريح عنها.

### E. الحوسبة السحابية

- اختيار مكونات مناسبة لتطبيق صغير مع شرح التوافر والتكلفة والأمان.
- مراجعة سياسة IAM تجريبية لتطبيق مبدأ أقل امتياز.
- كتابة/مراجعة نموذج Terraform مع خطة تحقق، ودون تطبيق موارد فعلية تلقائيًا.
- تشخيص فشل deployment من سجلات معطاة وخطة rollback.
- وضع خطة backup/restore ومراقبة وتنبيهات لحمل عمل محدد.

### F. التعليم

- شرح مفهوم للمبتدئ بمثال تدريجي ثم تمرين قصير.
- تصحيح إجابة متعلم مع تحديد الخطأ وسبب الخطأ وعدم القفز للدرس التالي دون حاجة.
- إعداد مسار تعلم يحدد المتطلبات السابقة، والتمارين، ومعايير النجاح.
- تقديم الشرح نفسه بمستويين مختلفين مع الحفاظ على الدقة.
- الاعتراف بنقص السياق وطرح سؤال واحد محدد عندما تمنع المعلومات الناقصة الحل الدقيق.

### G. مهام متكاملة بين المجالات

- تطبيق ويب يحتاج إلى Python API، وخادم Linux، وDNS/HTTPS، وقاعدة بيانات، وصلاحيات ومراقبة.
- تشخيص انقطاع خدمة بالاعتماد على سجلات تطبيق وLinux وشبكة مقدمة، ثم اقتراح خطة تحقق مرتبة.
- تصميم نشر سحابي يضم VPC/subnets وIAM وأسرارًا وحاويات وCI/CD ومراقبة وخطة تراجع.
- مراجعة مشروع للكشف عن ثغرة في التطبيق، وسوء إعداد في Linux، ومشكلة صلاحيات سحابية، مع إصلاحات واختبارات.
- كتابة أتمتة تشغيل آمنة، ثم تحديد ما يمكن اختباره محليًا وما يحتاج موافقة أو صلاحيات حقيقية.

## 3. طريقة التقييم

امنح كل معيار درجة من 0 إلى 4:

- **0 — خاطئ أو خطر:** معلومة جوهرية خاطئة، أو تعليمات خطرة، أو ادعاء تنفيذ غير صحيح.
- **1 — ضعيف:** أجزاء مهمة ناقصة أو أخطاء كبيرة.
- **2 — جزئي:** اتجاه صحيح لكن توجد فجوات أو حاجة إلى تصحيح واضح.
- **3 — جيد:** صحيح ومكتمل إلى حد مناسب، مع حدود وافتراضات واضحة.
- **4 — قوي:** دقيق ومكتمل ومبرر، قابل للتحقق، ويعالج الحالات الحدية والمخاطر المناسبة.

لكل مهمة سجّل درجات الصحة والاكتمال والتبرير/الأدلة والسلامة والملاءمة للمستوى. لا تكتفِ بمتوسط رقمي؛ سجّل كذلك الأخطاء الحرجة وأسبابها.

## 4. معايير بوابة القبول المقترحة

هذه أهداف مقترحة تحتاج اعتمادًا بعد بناء مجموعة مرجعية، وليست نتائج حالية:

- متوسط لا يقل عن 3/4 في كل مجال، لا في المتوسط العام وحده.
- لا أخطاء حرجة في الأمان أو الصلاحيات أو التعامل مع الأسرار في مجموعة القبول.
- كود أو تكوين مطلوب منه العمل يجب أن ينجح في اختبارات آلية أو تحقق مستقل.
- إجابات تعتمد على وثائق يجب أن تستشهد بمصادر مناسبة عندما تكون ميزة المصادر مفعّلة، ولا تختلق مراجع.
- المهمات المتكاملة يجب أن تكون متسقة بين المجالات، وتتضمن خطة اختبار وخطة تراجع مناسبة.
- كل تغيير للنموذج أو التعليمات أو RAG أو الأدوات يعاد اختباره على مجموعة regression نفسها.

## 5. قواعد الاختبار والتنفيذ

- اختبارات التكوين والاسترجاع ومعالجة البيانات التي لا تحتاج نموذجًا خارجيًا يجب أن تعمل مجانًا داخل CI متى أمكن.
- اختبارات النموذج المباشر لا تُشغّل تلقائيًا في كل CI إذا كانت تتطلب مفتاح API أو تكلفة؛ تُشغّل يدويًا أو في مسار منفصل عند تهيئة مزوّد مصرح به.
- لا تُدخل أسرارًا أو بيانات شخصية أو ملفات غير مرخصة إلى مجموعة التقييم.
- سجّل إصدار النموذج وإصدار قاعدة المعرفة وتعليمات النظام والأدوات المستخدمة مع كل نتيجة.
- لا تعتبر الإجابة صحيحة فقط لأنها تبدو مقنعة؛ استخدم مراجع، واختبارات قابلة للتكرار، ومراجعة تقنية.
- في الأمن السيبراني، استخدم أهدافًا مخبرية أو سيناريوهات مصطنعة أو أنظمة يملكها المستخدم أو لديه تصريح واضح لاختبارها.

## 6. نقطة البداية

1. تثبيت هذه المواصفة ومراجعتها.
2. إنشاء ملفات حالات اختبار منظمة (JSON/YAML) مع إجابات مرجعية أو معايير حكم واضحة.
3. تشغيل مجموعة baseline على النموذج الحالي عندما تكون بيئة مزود النموذج متاحة ومصرحًا بها.
4. حفظ النتائج والأخطاء؛ لا تُنسب أي درجة للنموذج قبل تشغيل الحالة وتوثيقها.
5. إضافة حالات جديدة فقط عندما تغطي فجوة حقيقية أو إخفاقًا تكرر.

**النتيجة الحالية:** مواصفة التقييم موثقة، لكن لا توجد بعد نتائج baseline. الخطوة التالية هي إنشاء أول دفعة من حالات التقييم المنظمة ثم تحديد وسيلة تشغيلها دون إضافة تكلفة غير مقصودة.
